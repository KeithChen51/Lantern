# 内网 AI 源码更新指南（交付模板）

打包人员：将本文复制到交付包根目录，命名为 `AI更新指南.md`；补充本次版本、完整 main SHA、源码 ZIP 文件名与 SHA-256、上一交付基线（未知则明确写未知）、变更摘要、迁移/配置影响、实际验证与未验证项。不得保留未填写占位符。

## 给执行更新的 AI

你的任务是把这次交付的源码安全地同步到用户已有的内网灯塔仓库，保留内网历史、配置和数据，完成差异审阅与验证。先读取本文、包内 `manifest.json`、`SHA256SUMS`、部署说明和验证报告，以及目标仓库适用的协作规则。包内源码是交付基线，不意味着目标仓库所有独有文件都应该删除。

用户可这样发起：

> 请先阅读交付包内的 AI更新指南.md，再把包内源码更新到我指定的内网灯塔仓库。先检查仓库和交付基线，保留配置、数据及内网改动，在更新分支完成同步、验证和变更报告。当前授权不包含数据库迁移、生产部署、强制推送或删除未知文件。

## 1. 确认对象与基线

1. 确认用户提供的目标仓库绝对路径和交付包路径；检查当前分支、HEAD、remote、工作区改动及适用规则，不输出 remote 中的凭证。
2. 校验交付包、源码 ZIP 和文件清单的 SHA-256。读取版本源，确认与 manifest 一致。哈希只能证明文件完整性，不能替代可信传输来源。
3. 源码 ZIP 解压到仓库外的临时目录；防止绝对路径和 `..` 越界。源码根目录应直接含 package.json、src/、Jenkinsfile。不要把外层说明、日志、环境模板一起复制进源码树。
4. 确认内网上一交付版本、对应内网提交及后续修改。不能仅靠 package.json 判断代码完全一致。找不到上一基线时，明确记录“基线未知”，对删除和内网改动使用保守合并。
5. 检查未提交修改、未跟踪文件、被忽略的配置/数据。先形成可恢复备份或按用户授权保存现有改动；不得通过 reset/clean 让工作区看起来干净。不要把密钥加入 Git。
6. 从已确认的内网 dev 基线创建 `codex/import-<版本>` 分支，或使用符合内网规范的独立工作树。切换会影响现有改动时先隔离处理。

## 2. 同步规则

| 文件类别 | 处理规则 |
| --- | --- |
| .git 目录或文件、remote、Git 历史 | 保留，不替换、不重新初始化 |
| 实际 .env、密钥、证书、部署平台凭据 | 保留；仅按新版模板补配置项，不展示密钥内容 |
| 数据库、上传、存储、日志、备份、挂载目录 | 不作为源码清理；数据库另行备份，源码更新不迁移数据库 |
| 包内源码、资源、依赖锁文件、字体与离线依赖 | 对比后同步新增和修改；保持配套文件完整 |
| 内网定制代码、Jenkinsfile、部署脚本和配置 | 逐项审阅合并，保留必要适配并纳入新版构建逻辑，不能一律跳过或覆盖 |
| 旧仓库有、包内没有的文件 | 分类确认；包内不存在本身不是删除依据 |
| node_modules、.next 等生成目录 | 不作为交付源码复制；使用目标平台重新安装与构建 |

有上一交付基线时，以“上版交付源码 → 本版交付源码”和“上版交付源码 → 内网现状”两组差异做三方合并。上版有、本版删除且内网没有修改的受管源码可以移除；内网修改与外网删除冲突时，保留现场并报告冲突。内网新增文件默认保留并评估是否影响运行。

基线未知时，生成待删除候选清单并解释依据，不自动删除未知文件。能确定的新增/修改先继续完成。不要执行根目录通删、未经排除及预览的镜像同步、`git clean -fdx` 或 `git reset --hard`。

涉及文件操作时，确认解析后的源/目标绝对路径都在指定目录内；不要跟随未知链接或目录联接清理目录。

## 3. 一致性与配置

- 保持 src/content/releases.json、package.json、package-lock.json、CHANGELOG.md 一致，不为导入内网而自行更改版本。
- 保持 Action 内容源、manifest、生成数据、路由映射配套；保留全部 Prisma 迁移历史。
- public/fonts/ 字体、许可证、manifest 与 CSS 配套同步；字体请求必须同源，无需终端安装或公网 CDN。
- deploy/offline/ 的归档和 SHA256SUMS 配套同步。不得用 Windows node_modules 或 runtime 替代 Linux 运行依赖。
- 配置差异只列变量名、用途、必需性和是否已配置；不打印真实密钥。
- 以本次部署说明为准核对 Node/系统架构、数据库驱动、模型与 embedding、持久化目录。源码导入不自动开启服务或执行初始化。

## 4. 验证与交付

先查看完整 diff、新增/删除清单，再执行适用验证：

```bash
git diff --check
npm run releases:check
npm run check:fonts
```

安装依赖、构建和运行使用包内说明及内网镜像源；不得遇到依赖问题就悄悄切换公网。发布候选执行 npm test、npm run lint、npx tsc --noEmit、npm run build；若构建依赖 Linux 离线准备，按内网 build.sh / Jenkinsfile 顺序执行。缺少网络或运行环境时记录阻塞，不标为通过。

需要实际部署时，另按授权执行数据库备份/迁移、配置注入及业务验收。页面健康检查不替代模型问答、知识检索、管理写入与持久化验证。

有提交/推送/PR 授权后，仅提交已审阅文件，通过 PR 进入内网 dev。避免无审阅 `git add -A` 带入配置、数据或备份；禁止默认强推。没有授权时，保留可审阅改动和报告。生产部署不从“请更新源码”推断获得授权。

## 5. AI 必须输出的报告

- 外网版本、main 完整 SHA、源码 ZIP SHA-256；内网更新前后提交或尚未提交状态。
- 新增、修改、删除的文件摘要；保留的内网专有文件和适配。
- 合并冲突、待删除候选、仍需用户提供的信息。
- 环境变量、数据库迁移和持久化影响，禁止包含真实密钥。
- 每项验证的命令、结果和未执行原因。
- 源码同步、PR 合入、镜像构建、测试部署、生产部署分别是什么状态。
- 回退基线与方法；数据库/上传备份另行说明，不能把 Git 回退称为数据回滚。

如内网为适配而修改了源码，记录与交付 main 的差异和回补事项，不能声称仍是字节一致的原版交付。
