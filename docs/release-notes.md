# 版本与内网交付规范

## 版本对应什么

main 是本机确认可发送到内网的交付基线，dev 是日常集成分支。一次交付由「三段版本号 + main 完整提交 SHA」标识；压缩包另记 SHA-256。版本在进入 main 前确定，不等待内网测试或生产部署，不依赖 GitHub Release，也不要求创建 Git 标签。

流程：工作分支 → PR 到 dev → 交付评估及升版 → dev 到 main 的交付 PR → 从干净且已同步的本机 main 导出 → 内网测试 → 内网生产部署。

main 的含义是代码已准备好交付；内网测试通过、生产已部署是分别记录的环境状态。同一交付产物从测试晋级生产保持版本与校验值不变，重复传输同一产物也不升版。

## 什么时候必须升版

任何会改变交付源码、运行行为、知识或内容、依赖、配置或构建部署脚本的变更，在下一次进入 main 前必须形成新版本。不能因为内网尚未部署而继续沿用旧版本，也不能用同一版本号交付不同功能或修复。

日常开发提交及工作分支合入 dev 不逐次升版；一个交付批次汇总一次，按批次中影响最大的变化决定版本级别。dev 中尚未交付的版本记录可以继续调整；进入 main 后该版本即冻结，追加修复必须使用下一版本。

| 变化 | 版本规则 | 示例 |
| --- | --- | --- |
| 重大产品升级或不兼容的接口、数据、使用方式变化 | 第一位加一，后两位归零 | 1.1.2 → 2.0.0 |
| 新增功能、模块，或兼容的独立能力扩展 | 第二位加一，第三位归零 | 1.0.3 → 1.1.0 |
| Bug 修复、局部体验/内容调整、依赖及构建部署修复 | 第三位加一 | 1.1.0 → 1.1.1 |

纯协作说明、拼写和不进入运行产物的文档修订可以不升版，但 PR 必须说明原因；仍以新的 main SHA 区分。若修正的是运行配置、交付步骤或用户可见说明，可能影响交付使用，则按补丁版本处理。回滚使用原版本和原产物，不重新包装旧内容为新版本。

内网发现问题时，将修复同步回工作分支，经 dev 形成下一交付版本后再传输；不得在同一版本下保留仅存在于内网的源码补丁。紧急例外按 AGENTS.md 记录授权、差异和回补，不能称为原版产物。

## 唯一版本来源与更新步骤

1. 在交付工作分支修改 src/content/releases.json，新增记录放在数组最前面，保留历史记录；当前版本始终取第一项。
2. 记录版本、标题、简介及分组变化。覆盖整个交付批次，说明实际能力及必要限制，不直接复制 Git 日志、不将待配置或未开放能力写成已可用。
3. date 表示「main 交付版本形成日」（YYYY-MM-DD，Asia/Shanghai），不是传输日、内网测试日或生产部署日。dev 准备阶段可用 null；交付 PR 合并 main 前须填实际交付日期。1.0.0 是历史首版基线，其日期未知，保留 null，不补造。若合并跨日，合并前校正日期。
4. 执行 npm run releases:sync，生成 package.json、package-lock.json 与 CHANGELOG.md。不要分别手工修改这些版本字段或生成日志。
5. 执行 npm run releases:check，并检查差异。交付 PR 对照当前 main 核对版本已按规则递增、日期准确、更新说明覆盖完整范围；纯文档例外必须写明。
6. 按 AGENTS.md 完成相应验证与 dev → main 评估。交付内容冻结后合并并记录最终 main SHA。

现有 releases:check 自动检查三段数字格式、版本降序和唯一性、日期格式，以及 package/CHANGELOG 一致性；build 前也执行此检查。它目前不自动比较 main 的版本差异，也不证明功能、交付日期或部署状态真实，这些由交付 PR 评估核对。

## 交付和部署如何记录

从干净的本机 main 或指定 main 提交导出源码，先确认其包含已评估的交付 PR。不要从旧工作分支、脏工作区或尚未整合的工作树拼包。交付包建议命名 lantern-1.1.0-<短SHA>.zip；版本号之外记录完整 SHA 和交付包 SHA-256。包内不带凭证、个人配置或运行数据。

沿用 Issue / PR 或内网 CODING 记录，不增加 GitHub Release 依赖。每次交付至少记录：

| 字段 | 说明 |
| --- | --- |
| 交付版本 / main 完整 SHA / 形成日期 | 确认具体源码基线 |
| 文件名 / SHA-256 / 实际传输日期 | 确认实际发送的产物，尚未传输填待传输 |
| 内网源码 SHA / 镜像摘要或制品标识 | 记录内网接收、构建后的对应关系 |
| 测试状态 / 时间 / 证据 | 待测试、通过或失败；不能用本机构建替代 |
| 生产状态 / 时间 / 回滚版本 | 未部署、已部署或已回滚，与测试状态分开 |

在内网从交付源码构建镜像时，也应固定依赖和构建输入，记录最终镜像摘要；测试通过后优先晋级同一镜像到生产。若重新构建产生不同产物，应重新校验和测试，不能只凭相同版本号认定通过。

## 页面显示

通知与 /updates 共用 releases.json，显示随当前代码交付的版本，不读取其他环境的最新版本。页面日期对应交付记录，不能用来推断所在环境何时部署。

通知打开或访问更新页后，在当前浏览器保存已读版本；升版后再次提示。清除浏览器数据或更换浏览器可能重新提示；不包含账户间同步，禁用存储时仍能查看。
